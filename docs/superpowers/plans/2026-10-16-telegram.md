# Telegram Messages Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A Telegram bot inside the CRM links staff by shared contact and sends lesson reminders, unmarked-attendance nudges, lesson-change and salary messages, each exactly once.

**Architecture:** Pure planning (`telegram-plan.ts`) decides which messages are due and their texts; a small queue
(`telegram-queue.ts`) stores each message once by key and delivers it through a fetch-based client with retries; the bot
(`telegram-bot.ts`) long-polls for Start/contacts and runs a minute timer, started from `instrumentation.ts` only when
`TELEGRAM_BOT_TOKEN` is set. CRM actions enqueue change messages after saving.

**Tech Stack:** Next.js 15 (instrumentation, Node runtime), Prisma 6 SQLite, node:test, Telegram Bot API over `fetch`.

**Spec:** docs/superpowers/specs/2026-10-16-telegram-design.md

## Global Constraints

- Token only in `.env` as `TELEGRAM_BOT_TOKEN`; never stored in the DB, shown on a page or logged. No token → bot off.
- Reminder 30 min before start; "not marked" 15 min after start; a message is due only within 10 minutes of its send time.
- Recipients: who teaches that day (teacher/assistant after substitutes); admins = active linked users with `staff.manage` get the unmarked list.
- Each message once (`TelegramMessage.key` unique); up to 3 tries, then FAILED. A Telegram failure never fails a CRM action.
- Linking only with the sender's own contact (`contact.user_id === from.id`), matched by `phoneKey` to **active** staff.
- Texts exactly as the spec's table (Uzbek), centre time (`centreToday`). No student data in messages.
- No bot library; one bot process (README). Stop the dev server before `db push`.

## Review Focus

- Server restart or a long Telegram outage → no burst of stale reminders; queued messages older than 2 hours are marked FAILED, not sent late (Task 2 test).
- A group whose teacher changed (teacher history) or with a substitute that day → the reminder goes to who teaches that day, never to both (Task 1 test).
- A staff member blocked or unlinked after a message was queued → not sent (Task 2 test).
- Telegram answers 403 (user blocked the bot) → the message FAILS once with the reason, no retries forever, and the chat is unlinked (Task 2 test).
- Two Start presses / contact shared twice, or a chat already linked to another person → one link, moved to the new person (Task 1 test).

### Task 2: Queue, client, bot

**Files:** Modify `prisma/schema.prisma` (model `TelegramMessage` per spec + `User.telegramMessages`); create `src/lib/telegram-client.ts`, `src/lib/telegram-queue.ts` (+ `telegram-queue.test.ts`), `src/lib/telegram-bot.ts`, `src/instrumentation.ts`.

**Interfaces:**
- Consumes: Task 1 `Outgoing`, `dueMessages`, `linkReply`.
- Produces:
  - `type TelegramClient = { sendMessage(chatId: string, text: string, extra?: object): Promise<void>; getUpdates(offset: number, timeoutSec: number): Promise<Update[]>; getMe(): Promise<{ username: string }> }`; `telegramClient(token: string): TelegramClient` (throws `TelegramError { status, description }` on `ok: false`).
  - `type QueueStore` (insert-if-new by key, list pending, mark sent/failed, user chat lookup, unlink) with `prismaStore()`; `enqueue(store, msgs: Outgoing[]): Promise<number>` (count new); `flush(store, client, now = new Date()): Promise<void>`.
  - `notify(msgs: Outgoing[]): Promise<void>` — enqueue + flush with the env client; no-op without token; never throws (used by actions).
  - `startBot(): void` — idempotent (guard on `globalThis`), long-poll loop + minute timer (`dueMessages` → `enqueue` → `flush`).
